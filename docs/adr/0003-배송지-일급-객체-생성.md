# ADR-0003: AddressBook 일급 객체 생성

## 상태
채택

## 배경 (이걸 왜 고민했고, 어떤 상황이었는가)
https://jaeseo0519.tistory.com/435?category=1039861

서비스에 도메인 규칙이 흩어져 있다고 생각하고 있었는데, 이를 어떻게 개선할지 찾아보다가 위 블로그를 보게되었다.
블로그에서는 Mock 사용을 지양해야 한다는 점과 이를 극복하기 위한 방법에 대해 다루고 있었다.

1. Mock 객체는 중요한 계약 변경을 감지하기가 어렵다.
    - 개발자가 정의한 결과를 반환할 뿐이기 때문에 실제 구현체의 계약 변경이 테스트에 자연스럽게 반영되지 않는다.
    - 이로인해 실패해야 할 테스트가 통과할 수 있는 가능성이 생긴다.
2. 구현에 결합된 테스트를 만들게 된다.
    - 테스트가 무엇을 달성했는가 보다 어떻게 구현했는지에 집중하게 된다.

2번을 쉽게 이해하기 위해 AI를 활용하여 코드로 예시를 만들었다.

```java
//대상코드

@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final PointRepository pointRepository;

    public Long placeOrder(Long userId, int amount) {
        int point = pointRepository.findPointByUserId(userId);
        int discounted = amount - point;

        Order order = new Order(userId, discounted);
        orderRepository.save(order);

        pointRepository.resetPoint(userId);
        return order.getId();
    }
}
```

```java
//Mockist 방식

@Test
void placeOrder_mockist() {
    // (1) 내부에서 뭘 호출하는지 미리 다 알고 stub해줘야 한다
    when(pointRepository.findPointByUserId(1L)).thenReturn(300);
    when(orderRepository.save(any(Order.class)))
        .thenAnswer(inv -> { inv.getArgument(0, Order.class).setId(10L); return null; });

    Long id = orderService.placeOrder(1L, 1000);

    // (2) 결과가 아니라 "호출했다는 행위"를 검증한다
    verify(pointRepository).findPointByUserId(1L);
    verify(orderRepository).save(argThat(o -> o.getAmount() == 700)); // 700 = 1000 - 300
    verify(pointRepository).resetPoint(1L);
    verifyNoMoreInteractions(pointRepository, orderRepository);
}
```

```java
//상태 기반 방식

@Test
void placeOrder_stateBased() { // 실제 구현체 or fake 사용
    pointRepository.save(new UserPoint(1L, 300));

    Long id = orderService.placeOrder(1L, 1000);

    Order saved = orderRepository.findById(id).orElseThrow();
    assertThat(saved.getAmount()).isEqualTo(700);       // 달성한 결과
    assertThat(pointRepository.findPointByUserId(1L)).isEqualTo(0); // 포인트 소진됨
}
```

상태 기반 방식을 사용하면, placeOrder 메서드의 내부구조가 리팩토링 되어도(입력 -> 결과 상태는 그대로 일때) 테스트 코드에 변경이 생기지 않는다.
반면에 Mockist 테스트는 Stub된 메서드를 어떻게 반환할지 바꿔줘야하는 구현에 따른 변경점이 생긴다.

### Fake 객체
블로그에서는 Fake 객체로 테스팅하는 것에서의 한계점도 이야기하고 있다.
1. JPA의 영속성 컨텍스트 같은 복잡한 메커니즘을 구현하기 어렵다는 점 (Dirty Checking, lazy loading 등)
2. 데이터베이스와의 상호작용 없이 제대로 테스트하기 어렵다는 점
3. 동시성 문제와 같은 엣지 케이스를 테스트하기 까다롭다는 점

또한, 내가 FakeRepository를 만들면서 Repository의 인터페이스에 메서드가 별로 없을 때는 FakeRepository 구현이 쉽겠지만,
이게 계속 늘어남에 따라 관리해야하는 구현체가 2개가 되니 유지보수면에서 안좋을 것 같다는 생각이 들었다.

### 일급 객체
최종적으로, Service는 통합테스트로 테스트 해야하고, 도메인 규칙은 가능한한 Mock 사용을 지양하면서 테스트를 작성할 수 있는 방법으로 일급 객체를 언급했다.
일급 객체란, 변수에 담고·인자로 넘기고·반환하고·자료구조에 넣을 수 있는, 다시 말해 다른 평범한 값들과 똑같이 자유롭게 다뤄지는 객체를 말한다.
그리고 비즈니스 로직의 본질은 DB나 HTTP 같은 외부 잡음을 걷어낸 순수한 도메인 규칙을 표현하는 것이므로,
그렇게 규칙만 떼어낸 도메인 객체는 어디에도 의존하지 않아 자연스럽게 이런 일급 객체의 성격을 띠게 된다.

### 적용
일급 객체 사용의 느낌을 잡기 위해 리팩토링을 진행했다.
```java
//기존 코드
@Transactional
public void create(Long memberId, String recipientName, String recipientPhone, String address, String deliveryRequest, boolean isDefault) {
    int count = addressRepository.countByMemberId(memberId);
    if (count >= 10) throw new IllegalStateException("배송지는 10개까지 생성할 수 있습니다.");
    Address newAddress = new Address(memberId, deliveryRequest, recipientPhone, recipientName, address, false);
    newAddress = addressRepository.save(newAddress);

    if (count == 0 || isDefault) {
        applyDefault(memberId, newAddress);
    }
}
```

```java
//변경된 코드와 AddressBook 클래스

//변경 코드
@Transactional
public void create(Long memberId, String recipientName, String recipientPhone, String address, String deliveryRequest, boolean isDefault) {
    AddressBook book = new AddressBook(addressRepository.findAllByMemberId(memberId));
    book.add(new Address(memberId, deliveryRequest, recipientPhone, recipientName, address, isDefault));
    addressRepository.saveAll(book.getAddresses());
}

//AddressBook
public class AddressBook {

    private static final int MAX_SIZE = 10;

    @Getter
    private final List<Address> addresses;

    public AddressBook(List<Address> addresses) {
        this.addresses = addresses;
    }

    public void add(Address address) {
        int size = getSize();
        if (size >= MAX_SIZE)
            throw new IllegalStateException("배송지는 " + MAX_SIZE + "개까지 생성할 수 있습니다.");

        if (addresses.isEmpty()) {
            address.setAsDefault();
            addresses.add(address);
            return;
        }

        if (address.getIsDefault()) {
            addresses.forEach(Address::unSetDefault);
            address.setAsDefault();
        }
        addresses.add(address);
    }
}
```

Service에 도메인 규칙을 드러내지 않고 주소 목록을 가지는 AddressBook이라는 순수 일급 객체를 생성해서 처리하였다.

## 결과
1. Service 코드가 매우 가벼워졌다.
2. 테스트 코드 작성이 용이해졌다.
