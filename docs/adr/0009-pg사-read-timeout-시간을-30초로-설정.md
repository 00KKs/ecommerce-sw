# ADR-0009: PG사 Read Timeout 시간을 30초로 설정

## 상태
채택

## 배경 (이걸 왜 고민했고, 어떤 상황이었는가)
가짜 PG 연동에서 지연(delay) 상황을 재현해보려고, PG 쪽 응답을 10초 늦추고 주문 서버의 confirm 요청 Read Timeout은 5초로 맞춰서 실험해봤다.  
그 결과 confirm 요청은 5초 만에 타임아웃(UNKNOWN)으로 끊기고, 곧바로 `lookupPayment`로 재확인을 시도했다.  
그런데 이 재확인이 일어나는 시점(5초째)에도 PG는 아직 처리 중(완료는 10초째)이라, 조회 결과가 `READY`(아직 미승인)로 돌아왔다.   
현재 로직은 `READY`를 "재시도 가능한 실패"로 취급해 `paymentService.aborted()`를 호출하고 주문을 결제 대기 상태로 되돌리는데, 문제는 이 결과가 **PG의 실제 최종 결과(성공이든 실패든)와 무관하게 항상 똑같이 나온다는 점**이었다.   
즉 10초 뒤 PG에서 실제로 승인이 완료되어 돈이 빠져나가든, 반대로 거절되어 끝나든, 우리 시스템은 이미 5초 시점에 "결제 대기"로 확정해버리고 그 이후의 진짜 결과는 아예 들여다보지도 못했다.  

이 실험으로 확인한 건 타임아웃 값 자체의 길이보다 더 근본적인 문제다: 클라이언트 타임아웃이 PG의 실제 처리 시간보다 짧으면, 재확인(lookup)조차 결론을 낼 수 없다.  
재확인이 의미를 가지려면 최소한 클라이언트가 기다리는 시간이 PG가 실제로 처리를 마치는 데 걸리는 시간보다는 길어야 한다.  
이 경험이, 앞서 확인한 토스페이먼츠 개발자 커뮤니티의 실제 문의 응답 — "응답 timeout을 길게 해주시기 바랍니다. 저희 권장 timeout은 30초입니다" — 와 맞물려서 30초를 최소 기준으로 삼게 된 실질적 계기가 되었다.  

## 결정
PG 승인(confirm) 요청의 Read Timeout을 30초로 설정한다.

## 이유
- 실험으로 직접 확인했듯, 타임아웃이 PG의 실제 처리 시간보다 짧으면 재확인(lookup) 자체가 무의미해진다. 재확인 시점에도 PG가 아직 처리 중이면 `READY`만 반복해서 돌아올 뿐, 진짜 성공/실패를 알아낼 방법이 없다.
- 토스페이먼츠 개발자 커뮤니티에서 실제로 "권장 timeout은 30초"라고 안내한 바 있어, 정상적인 PG 처리 시간을 오탐 없이 기다려줄 수 있는 최소 근거선으로 판단했다.
- 공식 문서의 60초보다는 짧지만, 이 프로젝트는 실제 운영 SLA를 맞춰야 하는 환경이 아니라 타임아웃·재확인·보상 흐름을 학습하기 위한 가짜 PG 연동이므로, "정상 응답은 통과시키고 진짜 지연 상황만 UNKNOWN으로 포착한다"는 목적에는 30초로도 충분하다고 봤다.

## 검토한 대안들
- **5초 (실험에 사용한 값)** — 직접 겪은 문제. PG 처리 시간(10초)보다 짧아, confirm과 재확인 모두 결론을 내리지 못하고 항상 "결제 대기"로 남는 오류를 일으킴. 이 경험이 이번 결정의 직접적인 계기가 되었다.
- **60초 (공식 문서 권장값)** — 더 안전하지만, 이 프로젝트에서 타임아웃 시나리오를 반복적으로 재현하며 학습하기엔 대기 시간이 불필요하게 길어짐.
