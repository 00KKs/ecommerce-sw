# ADR-0016: 결제 결과의 주문 반영을 단일 진입점(applyPaymentOutcome)으로 수렴

## 상태
채택

## 배경 (이걸 왜 고민했고, 어떤 상황이었는가)
결제 결과가 주문에 반영되는 경로가 두 개로 늘어났다.

1. **동기 주문 경로** — `PlaceOrderUseCase`가 결제 결과를 받아 switch로 분기해 `orderService.confirm()` / `fail()`을 호출했다.
2. **조회 스케줄러 경로** — UNKNOWN 결제를 재확인한 뒤(ADR-0013), `PaymentOutcomeReactor`가 별도의 switch로 분기해
   `OrderPort.confirmOrder()` / `failOrder()`를 호출했다.

두 switch는 "어떤 결과면 주문을 확정하고, 어떤 결과면 실패시키고 재고를 복원하며, 어떤 결과면 보류하는가"라는
**같은 규칙을 각자 구현**하고 있었다(당시 코드에 `FIXME: 코드 중복` 주석).

이 구조에서는 규칙이 바뀌면(예: retryable 실패 처리, UNKNOWN 추가) 두 곳을 함께 고쳐야 했다.
한쪽만 바뀌면 같은 결제 결과가 경로에 따라 다르게 반영될 수 있었다.
또 결제 쪽이 `confirmOrder` / `failOrder`를 직접 골라 호출하므로, 주문 상태를 어떻게 바꿀지를 결제가 정하고 있었다.

## 결정
결제 결과를 주문에 반영하는 진입점을 `OrderService.applyPaymentOutcome(PaymentResult, orderId)` 하나로 둔다.

```java
@Transactional
public Order applyPaymentOutcome(PaymentResult paymentResult, Long orderId) {
    return switch (paymentResult) {
        case CONFIRMED ignored -> confirm(orderId);   // 이미 CONFIRMED면 그대로 반환
        case FAILED ignored    -> fail(orderId);      // 이미 PAYMENT_FAILED면 그대로 반환 (재고 복원 1회)
        case PENDING ignored   -> getByIdWithItems(orderId);
    };
}
```
- OrderPort(결제 → 주문)는 applyPaymentOutcome 하나만 노출한다. 결제는 주문의 confirm / fail을 직접 고를 수 없다.
- 모든 경로가 이 진입점을 통과한다.
  - 동기 주문: PlaceOrderUseCase → OrderService.applyPaymentOutcome
  - 조회 스케줄러: PaymentLookupScheduler → PaymentOutcomeReactor → OrderPort → OrderService.applyPaymentOutcome
  - 대사 스케줄러: OrderReconciliationScheduler → OrderService.applyPaymentOutcome
- 결제 결과를 주문용 결과로 바꾸는 번역은 결제 쪽(PaymentResultTranslator)이 맡는다(ADR-0014).
주문은 번역된 결과(CONFIRMED / FAILED / PENDING)만 보고 자기 상태를 바꾼다.

## 이유
- 규칙이 한 곳에만 존재한다. 결제 결과에 따른 주문·재고 처리 규칙을 바꾸면 모든 경로에 동시에 반영된다. 경로별로 결과가 갈리는 일이 구조적으로 사라진다.
- 멱등성을 한 곳에서 보장한다. 이미 확정되었거나 이미 실패한 주문은 다시 처리하지 않으므로, 여러 경로가 같은 주문에 같은 결과를 반영해도 재고는 한 번만 복원된다. 동기 경로가 실패한 뒤 스케줄러가 다시 반영하는 복구 흐름이 이 성질에 기댄다.
- 판단의 소유자가 맞는다. "주문 상태를 어떻게 바꿀지"는 주문의 규칙이므로 주문 서비스가 소유한다(ADR-0005). 결제는 "결제가 어떻게 되었는지"만 알린다.
- 새 경로를 추가하기 쉽다. 대사 스케줄러를 추가할 때 주문 반영 로직을 새로 작성하지 않고 진입점만 호출했다.

## 검토한 대안들
- 경로별 switch 유지 (기존) — 각 경로가 독립적이라 이해는 쉽지만, 규칙이 중복되고 경로 간 불일치 위험이 있다.
- OrderPort에 confirmOrder / failOrder를 노출하고 결제 쪽에서 선택 — 포트는 단순하지만, 주문 상태 전이 판단이 결제로 샌다.
- 결제 결과 이벤트를 발행하고 주문이 구독 — 결합도는 가장 낮지만, 현재 단일 애플리케이션·동기 흐름에서는
이벤트 유실·순서·재처리라는 새 문제를 들여올 만큼의 이점이 없다고 판단했다.

## 결과
- 판단의 소유자가 맞는다. "주문 상태를 어떻게 바꿀지"는 주문의 규칙이므로 주문 서비스가 소유한다(ADR-0005). 결제는 "결제가 어떻게 되었는지"만 알린다.
