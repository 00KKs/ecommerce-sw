# ADR-0014: 결제 결과를 결제 내부용과 주문용으로 분리

## 상태
채택 (ADR-0008의 결과 타입 구조를 대체)

## 배경 (이걸 왜 고민했고, 어떤 상황이었는가)
ADR-0008에서는 하나의 `PaymentResult`(`SUCCESS | PAYMENT_FAILED(stage)`)를 결제와 주문이 함께 사용했다.
이후 결제 흐름이 구체화되면서 이 구조에 문제가 생겼다.

1. **결제 쪽 상태가 늘어날 때마다 주문이 함께 바뀌었다.**
   타임아웃 대응으로 UNKNOWN이 추가되고, confirm 실패에 retryable 구분이 생기면서(ADR-0012) 결과 케이스가 늘었다.
   그런데 주문 입장에서 필요한 건 "확정 / 실패 / 보류" 셋뿐인데, 결제 쪽 케이스가 추가될 때마다
   `PlaceOrderUseCase`·`OrderService`의 switch까지 수정해야 했다.
2. **주문이 결제의 내부 사정을 해석하고 있었다.**
   "retryable 실패면 재고를 보류한다", "initiate 실패면 재고를 복원한다" 같은 판단이 주문 쪽 분기에 흩어져,
   결제 결과의 의미를 결제가 아닌 주문이 정하고 있었다. 이는 ADR-0007의 port/adapter 경계와도 맞지 않았다.
3. **stage 중첩 구조가 실제 차이를 담지 못했다.**
   initiate 실패와 confirm 실패는 "어느 단계냐"뿐 아니라 가진 정보 자체가 다르다(paymentKey, retryable 유무).
   `PAYMENT_FAILED(PaymentFailedStage)`로 한 번 감싸면 switch가 두 단계로 중첩되고, 단계별 필드 차이가 바깥에서 보이지 않았다.

## 결정
결제 결과를 두 개의 sealed interface로 분리하고, 결제 쪽에서 주문용으로 번역해 넘긴다.
sealed interface + switch 사용(ADR-0008)은 그대로 유지한다.

```java
// 결제 내부용: 무슨 일이 일어났는가 (payment.application)
sealed interface PaymentResult {
    record PAYMENT_INITIATE_FAILED() implements PaymentResult {
    }

    record PAYMENT_CONFIRM_FAILED(@Nullable String paymentKey, boolean retryable) implements PaymentResult {
    }

    record SUCCESS(String paymentKey) implements PaymentResult {
    }

    record PAYMENT_UNKNOWN(String paymentKey) implements PaymentResult {
    }
}

// 주문용: 주문을 어떻게 해야 하는가 (order.port.dto)
sealed interface PaymentResult {
    record CONFIRMED(String paymentKey) implements PaymentResult {
    }

    record FAILED() implements PaymentResult {
    }

    record PENDING(@Nullable String paymentKey) implements PaymentResult {
    }
}
```

## 이유
- 변경이 한쪽에 갇힌다. 결제 쪽에 케이스가 추가돼도 Translator의 switch에서 컴파일 에러가 나고, 그 자리에서 "주문에게는 무엇인가"만 정하면 된다. 주문 코드는 바뀌지 않는다.
- 판단의 소유자가 명확해진다. "이 결제 결과가 주문에게 확정인가, 실패인가, 보류인가"는 결제를 가장 잘 아는 결제 쪽이 판단한다(ADR-0005·0007과 같은 방향).
- 주문의 분기가 주문의 관심사만 표현한다. 주문은 세 가지 경우만 처리하면 되고, 스케줄러 경로(PaymentOutcomeReactor)와 동기 주문 경로가 같은 applyPaymentOutcome을 재사용할 수 있다.
- 있을 수 없는 상태 조합을 막는다는 ADR-0008의 목적은 유지된다. 오히려 stage 중첩을 없애 단계별 필드 차이(initiate 실패에는 paymentKey가 없음 등)가 타입에 바로 드러난다.

## 검토한 대안들
- 하나의 타입 유지 (ADR-0008 구조) — 타입이 하나라 단순하지만, 결제 케이스가 늘 때마다 주문 분기가 함께 바뀌고 결과 해석 책임이 주문으로 샌다.
- 주문 쪽에 enum(CONFIRMED/FAILED/PENDING)만 넘기기 — 단순하지만, 확정·보류 시 응답에 필요한 paymentKey를 함께 전달할 수 없다.
- stage 중첩 유지 — 실패 단계 구분은 되지만, 단계별로 다른 필드를 표현하려면 결국 stage 안에 또 record가 필요해 구조만 깊어진다.
