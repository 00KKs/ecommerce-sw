# ADR-0006: 서비스 의존과 리포지토리 직접 접근의 선택 기준

## 상태
채택

## 배경 (이걸 왜 고민했고, 어떤 상황이었는가)
ADR-0005에서 카테고리 검증을 CategoryService에 위임했다.
그런데 다른 곳에서는 다른 서비스의 리포지토리를 직접 사용하는 경우도 생겼다.
어떤 경우에 서비스를 의존할지, 어떤 경우에 리포지토리를 직접 사용해야 할지의 일관된 기준이 필요했다.

두 가지 사례가 있었다.

1. 상품 생성 시 카테고리 검증 — CategoryService에 위임
```java
public void create(Long categoryId, String name, String description) {
    categoryService.validateLeafForProduct(categoryId);  //서비스 의존
    productRepository.save(new Product(categoryId, name, description));
}
```

2. 상품 판매상태 변경 시 SKU 조회 — SkuRepository 직접 사용
```java
public ProductStatusResponse changeStatus(Long productId, ProductSaleStatus status) {
    Product product = getById(productId);
    List<Sku> skus = skuRepository.findAllByProductId(productId);  //리포지토리 직접

    ProductSalePolicy policy = new ProductSalePolicy(skus);
    policy.validateTransitionTo(status);

    product.changeStatus(status);
    productRepository.save(product);
    return new ProductStatusResponse(product.getId(), product.getSaleStatus());
}
```

두 경우 모두 다른 애그리게이트의 데이터가 필요하지만, 
하나는 서비스를 의존하고 다른 하나는 리포지토리를 직접 사용한다.

## 결정
판단이 개입(서비스 로직이 들어가면)하면 그 판단을 소유한 서비스에 의존하고, 데이터(사실)만 필요하면 리포지토리를 직접 사용한다.

- 카테고리 검증: "최하위 카테고리인가"는 카테고리의 규칙에 대한 판단이다.
  이 판단을 CategoryService가 소유하므로 서비스에 위임한다.
- SKU 조회: 필요한 것은 SKU의 상태 목록이라는 사실이며, "SELLING SKU가 있는가"의
  판단은 ProductSalePolicy가 별도로 수행한다. 리포지토리는 데이터만 제공하므로 직접 사용한다.

## 이유
- 두 경우 모두 내부적으로 조회는 하지만, 조회가 목적인지 판단이 목적인지가 다르다.
  카테고리 검증은 조회를 수단으로 "최하위인가"를 판정하는 것이 목적이고,
  SKU 조회는 상태 목록을 얻는 것 자체가 목적이며 판단은 policy가 따로 한다.
- 판단(규칙)을 소유한 서비스를 거치지 않고 리포지토리로 우회하면, 그 규칙이 호출하는
  쪽으로 새어나간다. ProductService가 countDescendants를 직접 호출하면 최하위 판정
  규칙이 ProductService에 박히게 된다.
- 리포지토리는 데이터 접근의 종점이라 다른 서비스를 호출하지 않는다. 여러 서비스가
  같은 리포지토리를 의존해도 순환이 생기지 않는다. 반면 서비스끼리 서로 호출하면
  순환 의존이 발생할 수 있다.

## 결과
- 판단이 필요한 검증은 소유 서비스에 위임하여, 규칙이 한 곳에 응집되고 우회로 인해
  깨지지 않는다.
- 단순 데이터 조회는 리포지토리를 직접 사용하여, 불필요한 서비스 의존과 순환을 피한다.
- 판단 여부가 애매한 경우 "그 값을 얻는 데 해당 도메인의 규칙/판단이 개입하는가"를
  기준으로 삼는다. 개입하면 서비스, 저장된 사실이면 리포지토리다.
