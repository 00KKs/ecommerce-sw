# ADR-0007: 패키지 간 경계를 명확하게 나타내기 위해 Port/Adapter 패턴 도입

## 상태
채택

## 배경 (이걸 왜 고민했고, 어떤 상황이었는가)
SKU 생성 시 재고를 0으로 함께 초기화해야 한다는 내부 규칙을 추가하면서, 
sku 패키지가 stock 패키지의 기능을 호출해야 하는 상황이 발생했다. 
기존에는 controller → service 네이밍만 사용하고 있었기 때문에, 
sku가 stock의 `StockService`를 직접 참조하는 방식이 가장 단순한 선택지였다. 
하지만 직접 참조 시 sku 패키지가 stock의 내부 구현(엔티티, 리포지토리, 서비스의 모든 public 메서드)까지 알게 되어, 
stock 내부를 변경할 때마다 sku가 영향을 받을 위험이 있었다. 변경이 다른 도메인으로 전파되지 않도록 경계를 명확히 할 필요가 있었다.

## 결정
도메인(패키지) 간 호출이 필요한 경우, 인터페이스(Port)는 호출하는 쪽(소비자) 패키지에 정의하고, 그 구현체(Adapter)는 호출받는 쪽(생산자) 패키지에 둔다.   
ex) sku가 재고 초기화를 요청해야 하므로, `StockInitializer` 인터페이스는 `sku` 패키지에 두고, 이를 구현하는 `StockAdapter`는 `stock` 패키지에 둔다.  
도메인 내부(같은 패키지 안, 예: `SkuController → SkuService`)에서는 기존 controller/service 네이밍을 그대로 유지한다. Port/Adapter는 패키지(도메인) 경계를 넘는 호출에만 적용한다.
Adapter 클래스를 package-private으로 감춰 외부 패키지에서 접근할 수 없도록 한다.
Adapter 클래스에서 service를 사용하여 계층을 명확하게 구분한다. (직접 도메인을 다루지 않도록 설계한다.)

## 이유
인터페이스를 소비자가 필요한 만큼만 좁게 정의함으로써, sku가 stock에게 실제로 무엇을 기대하는지가 코드로 드러난다.  
인터페이스가 소비자 쪽에 위치하므로, 소비자 입장에서는 생산자의 존재조차 모르게 된다. (sku 입장에서는 자신의 패키지 안의 interface만 알면 됨)
서비스들이 엉켜 참조순환 문제가 발생할 수 있는 문제를 방지할 수 있다.

## 검토한 대안들
SkuService가 StockService 직접 사용 - 구현이 매우 간단하지만, Stock 변경 사항 생길 시 Sku에도 전파 가능한 문제
이벤트 기반 연동 - 의존성을 완전히 제거할 수 있지만, "SKU 생성 시 재고가 항상 함께 생성되어 있어야 한다"라는 즉각적인 일관성 요구와 맞지 않음
