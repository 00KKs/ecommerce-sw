# ADR-0013: 결과 불명 결제의 재확인을 스케줄러에 위임하고, READY는 같은 멱등키로 재승인

## 상태
채택

## 배경 (이걸 왜 고민했고, 어떤 상황이었는가)
ADR-0009의 실험에서, confirm이 타임아웃(UNKNOWN)되면 요청 흐름 안에서 곧바로 `lookupPayment`를 호출하고,
조회 결과가 `READY`(아직 미승인)이면 `paymentService.aborted()`로 처리했다.

이 구조에는 두 가지 문제가 있었다.
- 재확인 시점에 PG가 아직 처리 중이면 항상 `READY`가 나오고, 우리 시스템은 PG의 실제 최종 결과와 무관하게 결과를 확정해버린다.
  이후 PG에서 승인이 완료되어도 이를 다시 들여다보지 않는다.
- 재확인을 요청 흐름 안에서 하므로, PG가 느릴수록 사용자 응답과 요청 스레드 점유 시간이 함께 늘어난다.

## 결정
- confirm 결과가 UNKNOWN이면 Payment를 UNKNOWN으로 기록하고 즉시 응답한다(주문은 PAYMENT_PENDING, 재고 보류).
- 재확인은 `PaymentLookupScheduler`가 수행한다. 10→20→40→60초 + 지터로 백오프하며, 4회를 초과하면 MANUAL_REVIEW_REQUIRED로 전환한다.
- 조회 결과가 `READY`이면 실패로 확정하지 않고, **최초 confirm과 같은 멱등키로 재승인**을 요청한다.

## 이유
- `READY`는 "실패"가 아니라 "아직 결론 나지 않음"이다. 이를 실패로 확정하면 PG에서 승인이 완료된 경우 돈과 주문이 어긋난다.
- 멱등키를 Payment 생성 시점에 저장해 두었으므로(ADR-0011), 앞선 confirm이 PG에서 처리 중이었더라도 같은 키로 재요청하면 중복 승인 없이 같은 결과를 받을 수 있다.
- 재확인을 비동기로 분리하면 사용자 응답 시간이 PG 지연에 끌려가지 않는다.

## 검토한 대안들
- **요청 흐름 안에서 즉시 재조회 (기존)** — PG 처리 중이면 결론을 낼 수 없고, 응답이 지연된다.
- **READY를 계속 조회만 반복** — PG가 confirm 요청 자체를 받지 못한 경우(요청 유실) 영원히 READY로 남는다. 재승인이 있어야 수렴한다.

## 결과
- 타임아웃이 PG 처리 시간보다 짧아도 잘못된 실패로 확정되지 않는다. 다만 UNKNOWN과 재조회가 늘어나므로, ADR-0009의 30초는 유지한다.
- 재조회 한도를 넘기거나 PG 응답이 예상과 다르면(금액 불일치, CANCELED, NOT_FOUND) 자동으로 처리하지 않고 수동 확인으로 넘긴다.
