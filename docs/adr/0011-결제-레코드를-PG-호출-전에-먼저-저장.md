# ADR-0011: 결제(Payment) 레코드를 PG 호출 전에 먼저 저장

## 상태
채택

## 배경 (이걸 왜 고민했고, 어떤 상황이었는가)
실제 토스페이먼츠 흐름에서는 클라이언트가 SDK로 결제창 인증을 마친 뒤 paymentKey를 받아 서버에 승인을 요청한다.  
현재는 클라이언트 없이 이커머스 서버와 Fake PG 서버만 존재하므로, 결제창 인증 단계를 주문 서버가 Fake PG의 인증 API(initiate)를 직접 호출하는 방식으로 대체하고 있다.

기존 `processPayment`의 순서는 다음과 같았다.

    initiatePayment(orderId, amount)          -- PG 호출, paymentKey 수령
    → 성공 시에만 paymentService.ready(...)    -- 여기서 처음 Payment 생성 (paymentKey, 멱등키 포함)
    → paymentConfirmResolver.resolve(...)     -- 승인 요청

즉 **PG를 먼저 호출하고, 성공한 경우에만 Payment를 만드는 구조**였다. 이 순서에서 다음 문제가 드러났다.

- initiate가 FAILED면 Payment 없이 바로 리턴되어, 결제 시도가 있었다는 사실 자체가 어디에도 남지 않는다.
- initiate가 UNKNOWN(타임아웃 등)이면 PG 쪽에서는 paymentKey가 발급됐을 수도 있지만, 우리 DB에는 조회·복구의 기준이 될 레코드가 없다.
- 금액 검증의 기준(정답지)이 되어야 할 Payment가 PG 응답을 받은 뒤에 만들어져, 검증 순서가 뒤집혀 있었다.

## 결정
PG 호출 전에 Payment를 READY 상태로 먼저 저장하고, initiate 성공 후 paymentKey를 채운 뒤 승인을 요청한다.

    paymentService.ready(orderId, amount, idempotencyKey)   -- Payment(READY, orderId, amount, idempotencyKey) 저장
    paymentGateway.initiatePayment(orderId, amount)          -- (트랜잭션 밖) Fake PG 인증 API 호출
      ├ FAILED / UNKNOWN → PAYMENT_FAILED 반환 (Payment는 READY로 남음)
      └ SUCCESS          → paymentService.updatePaymentKey(paymentId, paymentKey)
    paymentConfirmResolver.resolve(...)                      -- (트랜잭션 밖) paymentKey + idempotencyKey로 승인 요청

- 멱등키는 Payment 생성 시 함께 저장한다. 생성 이후 바뀌지 않는 `orderId`, `amount`, `idempotencyKey`는 `updatable = false`로 매핑한다.
- `paymentKey`는 initiate 이후에 채워지므로 `updatable = false`를 적용하지 않고, `updatePaymentKey`를 통해서만 할당한다.
- paymentKey 저장은 confirm 호출 전에 커밋되도록 별도 서비스 호출로 분리한다.

## 이유
- **결제 시도가 PG 호출 결과와 무관하게 기록된다.** initiate가 실패하거나 결과를 알 수 없어도 READY 상태의 Payment가 남는다.
- **결과 불명 상태에서 복구할 근거가 생긴다.** initiate 타임아웃 시에는 READY Payment의 orderId로 PG를 조회할 수 있고, confirm 타임아웃 시에는 confirm 전에 커밋된 paymentKey로 조회한 뒤 같은 idempotencyKey로 재시도할 수 있다.
- **DB가 검증의 정답지가 된다.** PG 호출 전에 금액이 저장되어 있으므로, 이후 응답을 무엇과 비교해야 하는지가 명확해진다.
- **멱등키가 confirm 전에 확실히 저장된다.** Payment 생성 시점에 함께 저장되므로, confirm 재시도 시 같은 키를 재사용할 수 있다.
- **실제 토스 흐름과 모양이 같아진다.** 토스에서도 결제 레코드는 결제창을 열기 전에 만들어지고 paymentKey는 나중에 채워진다. 실제 클라이언트 흐름으로 전환할 때 initiate 호출 부분만 제거하면 되고, 승인 로직은 그대로 재사용된다.
